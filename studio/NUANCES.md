## 1. `waitForAnswer` брав СТАРУ відповідь замість нової (системний баг)

**Симптом:** у сценарії з двома запитами в одному чаті (запит → відповідь →
уточнення в тому ж чаті → друга відповідь) друга відповідь інколи виявлялась
БАЙТ-У-БАЙТ ідентичною першій — ІІ ще генерував нову відповідь, а скрипт уже
рухався далі з текстом старої.

**Причина:** `waitForAnswer(page)` шукав «поточну відповідь» як
`blocks.nth((await blocks.count()) - 1)` і чекав, поки текст ЦЬОГО блоку
стабілізується. Одразу після відправки нового повідомлення новий блок
відповіді в DOM ще міг не з'явитись — функція поллила СТАРИЙ (уже стабільний)
блок і поверталась миттєво зі СТАРИМ текстом.

**Виправлення** (`studio/lib/gemini.mjs`):
- `send(page)` тепер повертає кількість блоків відповіді ДО відправки:
  ```js
  export async function send(page) {
    const before = await page.locator(S.answer).count();
    // ...
    return before;
  }
  ```
- `waitForAnswer(page, { before })` спершу чекає, поки кількість блоків
  ПЕРЕВИЩИТЬ `before`, і лише тоді починає поллити стабільність тексту.

**Застосування в НОВИХ сценаріях:** завжди
`const before = await send(page); const answer = await waitForAnswer(page, { before });`
— ніколи голий `await send(page); await waitForAnswer(page);` для
follow-up-запиту в тому самому чаті (для ПЕРШОГО запиту в новому чаті це не
критично, бо `before` там і так 0).

**Стан по уроках:** виправлено в бібліотеці й у всіх викликах 2.5, 2.6, 2.7,
2.8, 2.9. Перевірено по стенограмах (`out/2-N/take-transcript.md`) — 2.5/2.6/2.7
на практиці НЕ постраждали (другі відповіді там завжди були змістовно інші),
пересъемка не знадобилась. 2.8 постраждав реально (спіймано і пересъемлено).

## 2. Багаторядкові константи, що друкуються В WORD — ламають регістр

**Симптом (урок 2.8):** норма, яку друкували в документ, розбилась на 4
«абзаци» з помилковими великими літерами посеред речення: «...отримання /
Адміністративної послуги / Екстериторіальності незалежно...».

**Причина:** `NORM` у `record/2-8.steps.mjs` — template literal з РЕАЛЬНИМИ
переносами рядків (зручно для читання коду):
```js
export const NORM = `Суб'єкт звернення має право на отримання
адміністративної послуги за принципом
екстериторіальності незалежно від місця
реєстрації задекларованого місця проживання.`;
```
`mouse.type()` друкує посимвольно, і кожен `\n` стає СПРАВЖНІМ Enter у Word.
Word автоматично капіталізує першу літеру нового абзацу.

**Виправлення:** на виклику, а не в самій константі —
`mouse.type(NORM.replace(/\n/g, ' '), { cps: 16 })`. Сама багаторядкова
`NORM` лишається як є, бо всередині промпту для Gemini (`PROMPT_EXPLAIN`)
перенос рядка нешкідливий — там немає автокапіталізації Word.

**Застосування:** перед тим, як передати БУДЬ-ЯКУ багаторядкову (для
читабельності коду) константу в `mouse.type()` для друку САМЕ В WORD —
прибирати внутрішні `\n`. Для друку в чат Gemini (`typeMultiline`) це не
проблема.

## 5. Виведення Chrome наперед — ТІЛЬКИ за PID, не за заголовком (безпека)

**Інцидент:** на репетиції уроку 2.9 (`--dry`) `frontGemini(page)` вивела
наперед ОСОБИСТЕ вікно Chrome користувача (чат про лазерний гравер) замість
demo-вікна зйомки. У `--dry` запис екрана вимкнено, але сама автоматизація
(набір тексту, кліки) виконується по-справжньому — продовжуй скрипт, і
текст промпту надрукувався б у живе особисте вікно користувача.

**Причина:** старий механізм (`stage.ps1`, дія `front`) шукав вікно так:
```powershell
Get-Process | Where-Object { $_.MainWindowTitle -like "*$Match*" } | Select-Object -First 1
```
— перше-ліпше вікно з підрядком у заголовку, у довільному порядку
`Get-Process`. Попередній «фікс» (матчити за ПОВНИМ поточним заголовком
сторінки CDP) не покривав момент одразу після `newChat()`: заголовок нової
розмови ще загальний, просто «Gemini», і під нього підходять ОБИДВА вікна
користувача.

**Структурне виправлення:**
- `studio/lib/stage.ps1`: дія `front` приймає `-TargetPid <pid>` — точний
  матч через `Get-Process -Id $TargetPid`, без пошуку за заголовком узагалі.
  (Параметр НЕ `-Pid` — це ім'я автоматичної read-only змінної PowerShell
  `$PID`, конфліктує.)
- `studio/lib/stage.mjs`: нова `bringChromeToFront()` — резолвить і кешує
  PID процесу, що слухає CDP-порт (`chrome.mjs` експортує `CDP_PORT`):
  ```powershell
  Get-NetTCPConnection -LocalPort 9222 -State Listen | Select -First 1 -ExpandProperty OwningProcess
  ```
  потім `ps(['-Action','front','-TargetPid', pid])`.
- `studio/lib/gemini.mjs`: `frontGemini()` (без аргументу `page` — більше не
  потрібен) викликає `bringChromeToFront()`.
- Стара `bringToFront(match)` (пошук за підрядком) ЛИШАЄТЬСЯ — для Word та
  інших вікон, де двозначності немає (Word завжди один).

**Перевірено:** двічі — напряму через PowerShell (PID з CDP-порту =
demo-вікно, НЕ особисте) і через повний прогін `--dry` (скріншот робочого
столу після rehearsal підтвердив правильне вікно).

**Застосування:** будь-який НОВИЙ сценарій запису викликає `frontGemini()`
(без аргументів) для Chrome — ніколи `bringToFront('Gemini')` чи подібний
підрядковий пошук. Уроки 2.2–2.8 записані зі старим шляхом — не
пересъемлені заднім числом (інцидент стався саме на репетиції, жоден
реальний дубль не постраждав).

## 6. `marks.json` може НЕ збігатися з реальним кадром відео — пастка скріншотів

**Симптом:** витяг кадру через `ffmpeg -ss <час-із-marks.json> -i take.mp4`
на позначці `2-vstavleno` (мало б показувати щойно вставлений і не
прибраний текст) показав ЩЕ НЕ вставлений текст (курсор мідиpe в заголовку).
Той самий час, за 5 секунд ДО реального моменту.

**Причина (ймовірна):** асинхронні PowerShell/COM-виклики (`pasteInWord()`
запускає окремий процес `powershell.exe`, що піднімає COM till Word) мають
змінну затримку старту, яка НЕ синхронізована з `mark()` (простий
`Date.now()` у скрипті запису). Для кроків БЕЗ PowerShell/Word (чистий чат,
урок 2.9) розбіжності не виявлено — `-ss` за `marks.json` збігався з
реальним кадром точно.

**Чому це НЕ ламає сам монтаж:** сегменти в `plan.ts` йдуть встик
(`to` сегмента N = `from` сегмента N+1) по СУЦІЛЬНОМУ відео — розбіжність
позначки зсуває лише межу, ДЕ саме змінюється швидкість програвання, а не
вирізає чи дублює кадри. Візуального стрибка/чорноти це не дає.

**Чому це ЛАМАЄ витяг скріншотів:** якщо покластись на голий
`ffmpeg -ss <mark> -i take.mp4`, можна витягнути кадр із НЕПРАВИЛЬНИМ
станом екрана (для лекцій-контенту сайту — реальна проблема).

**Робочий обхід, що спрацював:** витягувати кілька кадрів ШИРОКИМ вікном
навколо очікуваного часу (наприклад, кожні 5–10 с по всьому дублю — це й
так треба робити для перевірки на витік приватних даних, див.
[[video-recording-desktop-safety]]) і ВІЗУАЛЬНО перевіряти кожен перед
використанням, а не довіряти одному кадру за міткою наосліп.

**Ще одна пастка тут же:** `out/2-N/rehearsal/*.png` (скріншоти, зроблені
самим скриптом через `shot()`) СПІЛЬНІ між `--dry` і реальним прогоном —
якщо після реального дубля запустити ще один `--dry` (наприклад, для
перевірки фіксу), він перезапише `rehearsal/` своїми (нереальними для
фінального відео) скріншотами. Перевіряти timestamp файлу проти timestamp
`takes/take-NN.mp4` перед використанням, або витягувати напряму з
потрібного `take-NN.mp4`.

## 9. Автоматизація СПРАВЖНІХ сторінок Google (не нашого застосунку) — крихка

Урок 3.4 «Знеособлення» пройшов гладко: `selectInWord(mouse, text, text)` —
готове рішення для виділення одного фрагмента тексту через справжнє
протягування мишею (Find від Word, той самий текст в обидва аргументи).

Урок 3.6 «Налаштування приватності» — інша історія. Сторінка
`myactivity.google.com/product/gemini` (куди веде «Історія дій» з меню
Gemini) виявилась НАБАГАТО менш передбачуваною за сам застосунок Gemini:

- **Спливаюча підказка «Безпечніше з Google»** внизу сторінки з'являється й
  зникає непередбачувано, перехоплюючи кліки по сусідніх елементах.
- **Форсований клік (`{force: true}`) — небезпечний тут.** Один раз він
  влучив у зовсім інший пункт меню під підказкою замість цілі. Краще
  повторювати ЗВИЧАЙНИЙ клік (`locator.click({timeout})` у циклі з паузами),
  ніж форсувати — Playwright сам чекає стабільності елемента.
- **Клавіатурна навігація надійніша за клік мишею для випадаючих меню:**
  `ArrowDown`/`ArrowUp` + `Enter` після відкриття dropdown обходить всі
  проблеми з перехопленням кліків, бо клавіші не залежать від того, що
  візуально зверху.
- **Застряглий діалог переживає навіть `reload()` в тому самому табі.**
  Одного разу вікно «Дані про ваші дії не видалено» (наслідок ранішої
  спроби) продовжувало перехоплювати кліки на КОЖНІЙ спробі в тій самій
  вкладці, навіть після `page.reload()`. Допомогло тільки повне закриття
  вкладки (`page.close()`) і відкриття нової.
- **Багатокрокові підтвердження змін** (тут: зміна строку зберігання) —
  Google не застосовує зміну одним кліком: «клік по рядку» → «відкрити
  випадний список» → «обрати варіант» → «Далі» → «Підтвердити» (другий,
  окремий екран підтвердження з описом наслідків). Кожен крок — окрема
  точка відмови.

**Рішення для уроку 3.6:** після семи невдалих спроб довести повний потік
(включно зі зміною строку зберігання) до кінця — свідомо СПРОСТИЛИ дубль.
Записали тільки те, що стабільно працює (вимкнення історії, тимчасовий
чат), а рядок про строк зберігання лишили ВИДНИМ у кадрі (той самий
скріншот панелі) без живого клацання по ньому — і озвучили голосом
диктора, куди саме клацнути.

**Як застосовувати:** для будь-якого МАЙБУТНЬОГО уроку, що вимагає
автоматизації налаштувань САМОГО Google (а не нашого застосунку) —
закладати ЗАЗДАЛЕГІДЬ подвійний час на відладку, віддавати перевагу
клавіатурній навігації над кліками мишею для випадних меню, і бути готовим
спростити дубль (показати без повного клацання), якщо конкретна
підсторінка виявиться такою ж крихкою.

**Ще один інцидент цього уроку:** діагностичний скріншот `gdigrab`
(весь екран) один раз захопив ОСОБИСТЕ вікно Brave користувача з реальною
перепискою ChatGPT — файл видалено негайно. Причина та сама, що й раніше

дія», перед якою варто перевірити, що стіл вільний, а не лише перед
записом дубля.

## Поле «Знайти й замінити» в Word — `Ctrl+A` не очищає його

**Що сталося:** на реальному дублі уроку 4.4 (три послідовні заміни в
одному діалозі «Знайти й замінити») поле «Find what» на другій і третій
заміні показувало СЛИПЛИЙ текст усіх попередніх пошуків підряд —
"Іваненко Петре Васильовичум. Львів, вул. Шевченка, 1118-242" замість
чистого "118-24". Те саме — з полем «Replace with»
("[ЗАЯВНИК][АДРЕСА][НОМЕР]"). Причина: `mouse.key('^a')` (синтетичний
Ctrl+A) у ЦИХ конкретних полях Word — це комбобокси з історією пошуку, не
звичайні текстові поля — НЕ виділяє наявний текст. Клік у поле лишає курсор
десь усередині наявного рядка, і новий текст просто ДОПИСУЄТЬСЯ, а не
замінює. Помітно це тільки з ДРУГОЇ заміни в тому самому діалозі — перша
завжди виглядає чистою, бо поле й так було порожнім (нема що плутати з
Ctrl+A, що не спрацював).

**Наслідок був серйозніший за косметику:** якщо пошуковий рядок
перетворюється на сміття, «Замінити все» просто не знаходить збігів —
заміна МОВЧКИ не відбувається (скрипт не перевіряв кількість замін),
і в збереженому файлі персональні дані могли лишитися незамінними.

**Фікс:** `clearAndType()` у `word.mjs` — клік у поле, потім `{END}` і
`{BACKSPACE 100}` (курсор у кінець і бекспейси з запасом; поле точно
коротше 100 символів) ЗАМІСТЬ `Ctrl+A`. Це працює однаково в будь-якому
текстовому контролі Windows, на відміну від виділення. Використовується і
в `replaceInWordDialog()`, і в ручному коді першої заміни.

**Як застосовувати:** для БУДЬ-ЯКОГО нового поля вводу в Word/чужому
застосунку, яке потрібно очищати перед повторним використанням (не тільки
Find&Replace) — не покладатися на `Ctrl+A`, перевіряти дослідом, а типовий
безпечний варіант — `{END}` + `{BACKSPACE N}`.

## Word гортає документ до останнього збігу «Знайти» — треба повертати вручну

**Що сталося:** одразу після закриття діалогу «Знайти й замінити»
документ лишається прокрученим туди, де стався ОСТАННІЙ знайдений збіг
(найчастіше — ближче до кінця документа), а не на початку. У кадрі це
виглядало як майже порожня сторінка з одним рядком тексту вгорі — глядач
не бачив результат знеособлення взагалі. Помітив user: «слідкуй щоб ворд
документ нормально відображався в центрі екрана».

**Фікс:** виклик `scrollToTop()` (уже існував у `word.mjs`, дія `top` у
`word.ps1`) одразу після `closeReplaceDialog()`, перед тим як щось
показувати з документом у кадрі.

**Як застосовувати:** для будь-якого кроку в будь-якому уроці, де показ
документа йде ПІСЛЯ дій, що можуть змінити позицію прокрутки (Find,
вставка в кінець, скрол колесом) — явно повертати `scrollToTop()` або
`scrollToBottom()` перед кадром, а не покладатися на позицію «як лишилось».

## Word: поява бічної панелі приміток ЛАМАЄ вже складений рядок (реальний рендер-баг)

**Що сталося:** для картинки уроку 4.6 («документ у двох режимах перегляду»)
знімали Word-документ із track changes і приміткою на полях. Коли примітку
додавали ПІСЛЯ того, як абзац уже надрукований і перенісся на два рядки —
скріншот стабільно (дев'ять спроб поспіль) показував рядок із вирваним
шматком тексту посередині речення («...за потреб[пусто]довжується...»).
Це не проблема захоплення екрана (`gdigrab`) і не таймінг: помилка
відтворювалась однаково і з довгою паузою (1.5с), і з примусовим
перемальовуванням (зміна масштабу туди-сюди, прокрутка geть і назад до
початку документа) — жоден із цих прийомів не лікує. Прокрутка як «фікс»
одного разу навіть ЗНОВУ зламала вже правильний кадр.

**Причина (за результатом дослідів):** поява бічної панелі приміток звужує
робочу область сторінки — Word повинен перенести (re-wrap) уже складені
рядки на нову ширину. Коли це відбувається вже ПІСЛЯ того, як рядок
existing склався один раз (особливо якщо на тому самому рядку є ще й
позначка tracked-change), перемальовування цього конкретного рядка
збоїть — систематично, не залежно від паузи.

**Фікс — інший порядок дій, не інша пауза:**
1. Спершу надрукувати тільки заголовок.
2. Додати примітку НА ЗАГОЛОВКУ одразу — бічна панель з'являється ЗАРАЗ,
   поки решти абзаців іще немає.
3. Тільки ПОТІМ друкувати решту тексту — він одразу лягає в остаточній,
   вже звуженій ширині сторінки, без повторного переносу.
4. Track changes вмикати теж НАПРИКІНЦІ, безпосередньо перед самою
   правкою (не на самому початку) — інакше весь щойно надрукований текст
   піде як одна суцільна вставка, і саму правку («5»→«3») не буде видно
   окремим закресленням.

**Як застосовувати:** для будь-якого кадру, де в одному Word-документі
потрібні ОДНОЧАСНО примітка на полях (чи інша дія, що змінює ширину робочої
області — той самий клас проблем) І багаторядковий абзац — спершу
викликати зміну ширини (примітку), і лише тоді друкувати текст, який має
на неї спертись. Спроба «полагодити» готовий зламаний рядок через паузи чи
прокрутку — витрачений час, у цьому конкретному класі багів не працює.

## `pointAndClick` мовчки провалюється по елементу за межами видимої області

**Що сталося:** урок 5.4 (пошук на zakon.rada.gov.ua) — клік по посиланню
результату №6 зі списку з 6-ти не відкривав документ. Жодної помилки:
`pointAndClick` (спільний хелпер, `lib/human.mjs`) бере координати з
`locator.boundingBox()` і рухає туди СИНТЕТИЧНУ мишу Playwright напряму,
без вбудованого авто-скролу, який має звичайний `locator.click()`. Якщо
елемент нижче за видиму частину сторінки, `boundingBox()` повертає
координати ПОЗА реальним видимим кадром — клік «влучає в порожнечу» й
нічого не робить, без жодного винятку чи помилки в консолі.

**Чому важливо саме тут:** без перевірки результату дії (реального
підтвердження, що клік спрацював) цей провал ЛИШАЄТЬСЯ НЕПОМІЧЕНИМ — скрипт
рухається далі, ставить позначки (`mark()`) так, ніби все вдалося, і в
змонтоване відео потрапляє СТАРИЙ кадр (попередня сторінка) під закадровий
текст, який розповідає про зовсім інший документ. Це вже сталося в
реальному дублі уроку 5.4 до виправлення — опубліковане відео показувало
результат прикладу 1 («вигаданий номер») під час репліки про приклад 2
(«втрата чинності»).

**Фікс:**
1. Перед `pointAndClick(zpage, link)` перевірити `boundingBox().y` — якщо
   поза розумною видимою висотою (тут: `< 0` або `> 700`), проскролити
   плавно (`scrollBy`, не стрибком — той самий принцип, що й скрізь) до
   позиції елемента.
2. Після кліку ПЕРЕВІРИТИ результат дії напряму (тут: чи змінився
   `zpage.url()`), а не просто повірити, що дія відбулась. Якщо ні — лог і
   повторна спроба (до 3 разів), і лише після трьох невдач — кинути
   помилку (гучний збій набагато безпечніше за тихий).

**Як застосовувати:** для БУДЬ-ЯКОГО кліку через `pointAndClick` по
елементу, чия позиція на сторінці наперед не відома (список результатів
пошуку, динамічний контент) — не покладатися на «клік стався, бо винятку
не було»; перевіряти видимість елемента ПЕРЕД кліком і результат дії
ПІСЛЯ. Мовчазний провал у цьому класі автоматизації — гірший за явну
помилку, бо потрапляє в готове відео непоміченим.

## zakon.rada.gov.ua: посилання результату пошуку відкриває НОВУ вкладку

**Що сталося:** клік по посиланню документа зі списку результатів (урок
5.4) ніколи не змінював `zpage.url()` — перевірка «URL змінився» завжди
провалювалась, хоча live-скріншот показував, що документ насправді
відкрився. Причина: посилання відкриває результат у НОВІЙ вкладці
браузера, а не в тій самій сторінці. Скрипт продовжував дивитись на стару
(тепер фонову) вкладку.

**Фікс:** ловити подію `page` на контексті браузера одночасно з кліком
(`Promise.all([context.waitForEvent('page', {timeout}), pointAndClick(...)])`),
і якщо нова вкладка з'явилась — повернути її як «активну» замість старої;
виклик підміняє свою змінну `zpage` результатом. Стару вкладку зі списком
результатів після цього краще закрити (`.close()`), інакше вкладки
накопичуються з кожною повторною спробою.

**Як застосовувати:** для будь-якого посилання на сайтах, де НАПЕРЕД не
відомо, чи навігація станеться в тій самій вкладці, чи у новій (типово для
довідкових/каталожних сайтів) — перевіряти появу нової сторінки в
контексті, а не тільки зміну URL поточної.

## `getByText` знаходить ОДНАКОВИЙ текст двічі на тій самій сторінці

**Що сталося:** пошук статті закону за текстом заголовка (урок 5.4,
`getByText('Заборона відмови в прийнятті')`) послідовно приводив у
неправильне місце документа — навіть після заміни фрази на унікальнішу.
Діагностика показала: `.count()` для цього тексту повертає **2**, той
самий клас багів, що й дубльовані поля вводу (див. записи вище) —
десь на сторінці є прихована копія. `.first()` не гарантує, що дістанеться
саме видима.

**Фікс:** не покладатися на попередньо обчислену позицію (`boundingBox()`
ДО прокрутки) — натомість гортати ПЛАВНО невеликими кроками (по ~300px),
і після КОЖНОГО кроку перевіряти серед УСІХ збігів (`matches.nth(i)`),
який із них видимий (`isVisible()`) і чи його `boundingBox().y` вже у
видимій висоті екрана (`0..700`). Зупинитись, щойно знайдено.

**Як застосовувати:** для БУДЬ-ЯКОГО пошуку тексту на zakon.rada.gov.ua
(і, ймовірно, інших урядових сайтах зі схожою мобільною/десктопною
дублікацією розмітки) — спершу перевірити `.count()` для локатора; якщо
більше одного збігу, перебирати їх на видимість, а не брати `.first()`
наосліп. Це той самий урок, що й з полями пошуку, але для довільного
тексту, не тільки input/select.

## Стороння вкладка в тому самому Chrome — знімок/дубль показує ЇЇ, не Gemini

**Що сталося:** на репетиції уроку 4.8 обидва скріншоти (`shot()`) показали
СТАРУ вкладку zakon.rada.gov.ua (наслідок відлагодження уроку 5.4, яке
відкривало нові вкладки тим самим `page.context().newPage()`) замість
очікуваного Gemini з диктантом. Сама автоматизація (набір тексту, надсилання)
відпрацювала ПРАВИЛЬНО — стенограма показала вірну відповідь ІІ. Проблема
лише у ЗНІМКУ екрана: `grabFrame()`/справжній запис через `gdigrab` — це
завжди весь фізичний робочий стіл, а видно на ньому ту вкладку Chrome, яка
візуально АКТИВНА в браузері, незалежно від того, яким об'єктом `page`
керує Playwright-скрипт.

**Причина:** `frontGemini()` (=`bringChromeToFront()`) виводить наперед
саме ВІКНО Chrome за PID (див. запис вище про PID) — це не має жодного
стосунку до того, яка ВКЛАДКА всередині цього вікна активна. Якщо з
попереднього уроку (чи діагностики) лишилась відкритою стороння вкладка,
і вона в браузері «зверху» (останньою активованою), то саме вона потрапляє
в кадр, а не вкладка з Gemini, де насправді відбувається дія.

**Фікс:** на початку `setup()` кожного НОВОГО уроку — закрити всі вкладки в
контексті, крім тієї, з якою працює скрипт (`page.context().pages()`,
`.close()` для всіх, крім `page`), і явно `await page.bringToFront()`
(Playwright-виклик, що активує САМЕ ЦЮ вкладку всередині Chrome — на
відміну від `frontGemini()`, який працює на рівні вікна ОС).

**Як застосовувати:** для БУДЬ-ЯКОГО НОВОГО уроку, що записується в тому
самому довгоживучому Chrome-профілі (а це всі уроки) — на старті `setup()`
закривати сторонні вкладки й викликати `page.bringToFront()` ПЕРЕД
`frontGemini()`, а не покладатися, що потрібна вкладка й так «десь там»
активна. Особливо важливо одразу після уроків, чия автоматизація сама
відкриває нові вкладки (як 5.4) — навіть якщо той скрипт акуратно закриває
за собою, перерваний дубль (Ctrl+C, збій, ручне втручання) може лишити
вкладку висіти.

## Ізольований `browser.newContext()` — показати логаут-стан БЕЗ ризику для демо-сесії

**Що сталося:** уроку 1.5 потрібен скріншот екрана входу Gemini (не
залогінений стан, кнопка «Увійти» видима) — а демо-профіль Chrome
постійно залогінений (саме на цьому тримається вся автоматизація решти
курсу). Вийти з акаунта, щоб зняти один кадр, і потім заходити знову —
реальний ризик щось зламати в сесії, якою користуються десятки інших
сценаріїв.

**Фікс:** `browser.newContext()` (Playwright, той самий CDP-з'єднаний
`browser`) створює ПОВНІСТЮ ізольований контекст — без жодних кук
поточного залогіненого профілю, аналог нового Incognito-вікна, але без
ризику торкнутися основної сесії. Перехід на `gemini.google.com/app` у
цьому новому контексті сам показує чесний логаут-екран. Знімати саме
через `page.screenshot()` (сам Playwright, вміст сторінки), а не через
`grabFrame()`/`gdigrab` — новий контекст відкривається як ОКРЕМЕ вікно
Chrome, і виводити саме його на передній план рівня ОС (`bringChromeToFront`
працює по PID процесу, а не по конкретному вікну) ненадійно; `page.screenshot()`
обходить проблему фокуса вікна повністю. Контекст обов'язково `.close()`
після — не лишати висіти зайвий процес/вікно.

**Як застосовувати:** для будь-якого кадру, де потрібен ЧЕСНИЙ
незалогінений/початковий стан сервісу, а основний профіль залогінений —
не чіпати основну сесію (не логаутитись); відкривати новий ізольований
`browser.newContext()` і знімати `page.screenshot()` напряму.

відкривали й не заповнювали справжню сторінку
`accounts.google.com/signup`. Причини: (1) навіть без відправлення форми,
сам факт заповнення полів реального сайту реєстрації — це взаємодія з
антифрод-системою Google, прив'язаною до IP/відбитка того самого браузера,
яким користується весь демо-профіль курсу; ризик отримати капчу чи інше
обмеження на постійній сесії заради одного кадру не виправданий. (2) Це
дія з реальними наслідками поза нашим контролем (на відміну від
автоматизації Gemini/Word/zakon.rada.gov.ua — читання чи власний контент),
а не той клас ризику, який можна мовчки прийняти без прямого дозволу
користувача.

**Фікс:** побудовано власний HTML-макет форми (не скріншот) — та сама
візуальна мова курсу (кольори/шрифти з `edit/src/theme.ts`), з вигаданими
даними («Оксана Коваль») і трьома підказками-кулями, які повторюють
пункти уроку (email-варіанти, приватність дати народження, новий пароль).
Відрендерено через `page.goto('file://...')` + `page.screenshot()` у
тому самому CDP-з'єднаному браузері (не потрібен окремий headless-білд
Playwright — його на машині немає, `chromium.launch()` впаде з
«Executable doesn't exist»).

**Як застосовувати:** для будь-якого кадру, що вимагав би автоматизації
СПРАВЖНЬОЇ форми реєстрації/оплати/іншої чутливої дії на чужому сервісі —
за замовчуванням НЕ виконувати наживо; будувати власний точний макет тим
самим HTML+Playwright-screenshot прийомом. Це вже другий такий випадок
(перший — графіка-порівняння уроку 4.4, «власна графіка, не скріншот»),
тож технічно варто оформити як спільний хелпер, якщо знадобиться втретє.
